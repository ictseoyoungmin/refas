# RefAs 1.1.0 release readiness

RefAs 1.1.0 is release-ready only when the exact candidate commit passes the normal pull-request CI matrix and the protected Node 24 dogfood/release-audit chain, then the exact merged `main` commit passes post-merge CI before the release workflow creates or verifies `v1.1.0`.

This release closes the P01–P17 physical-semantics expansion. It adds no new semantic runtime behavior in the release-prep slice itself.

## Release identity

The exact release candidate must agree on all of the following:

- `package.json` version is `1.1.0`;
- `REFAS_VERSION` is `1.1.0`;
- new project state identifies runtime `1.1.0`;
- new whole-object certificates identify runtime `1.1.0`;
- public v1 project-state and certificate schemas continue accepting `1.0.0` through `1.0.4` artifacts;
- public `.../v1` contract namespaces are not renamed for the package minor version.

## Physical-semantics closure

The release includes the implemented P01–P16 contract stack:

- stable semantic physical identity independent of backend/runtime index;
- rigid-body dynamics and collision semantics;
- articulation and mechanism topology;
- coordinate/velocity/effort transmission mappings;
- actuator capability, controller profile, and optional runtime binding/calibration;
- digest-bound reusable physical asset bundles;
- representation-capacity preflight and one-way export;
- backend-independent normalization;
- typed cross-representation equivalence/loss/drift/unresolved/invalid validation;
- exact live declared divergence;
- scoped articulated/simulation/control/runtime readiness evidence.

The release audit must prove the physical runtime, schemas, and routed agent-facing contract leaves are present in the package. File existence in the repository alone is insufficient distribution evidence.

## Authority boundary

1.1.0 must preserve these non-negotiable distinctions:

- canonical physical construction is authoritative; backend artifacts are projections;
- semantic identity is not backend order, array position, motor/device index, or display name;
- `unknown` remains unresolved and does not receive convenience defaults;
- `inferred`/`engineered` physical values do not become observed manufacturer truth;
- equivalent transform/unit encodings normalize before P14 comparison;
- P14 `DRIFT` remains blocking unless the exact current field-scoped P15 declaration validates live;
- P16 readiness evidence validates against the current P10–P15 chain before generic certification;
- physical readiness cannot bypass typed live preflight through generic selectors or project-level certification;
- visual/source-fidelity certification remains independent of physical readiness.

## Integrated P17 evidence

`tests/integrated-physical-fixture.test.mjs` and `docs/integrated-physical-fixture.md` are the end-to-end closure evidence for the physical stack.

The fixture must continue proving:

- reusable module identity survives composition;
- fixed attachment interfaces remain distinct from virtual joints;
- two backend representations normalize equivalent quaternion/unit/Euler encodings without false drift;
- deliberate representable mass drift is detected;
- exact live P15 authority resolves only that drift;
- stale/substituted authority fails closed;
- the final positive path reaches P16 `runtime-ready` through typed live preflight and existing certification;
- control/runtime-only edits remain downstream-scoped;
- repeated runs reproduce identical P15-bound closure evidence.

## Exact-head CI gate

The PR exact HEAD must pass the repository CI matrix on Node 20, 22, and 24. The Node 24 protected path must also pass the complete dogfood/release chain, including:

```text
npm test
npm run test:python
npm run check
npm run dogfood
npm run dogfood:parameter-fit
npm run dogfood:pbr
npm run dogfood:hard-surface
npm run dogfood:assembly
node --test tests/integrated-physical-fixture.test.mjs
npm run release:audit
```

Historical green CI from P17 or an earlier release candidate is not release evidence for a changed head.

## Release-prep diff boundary

The 1.1.0 release-prep PR may change only release identity, backward-compatible state/certificate version acceptance, tests that assert the release identity, release/package audits, and current release documentation/demo metadata.

It must not introduce a new physical semantic contract, alter readiness meaning, weaken liveness checks, modify canonical physical behavior, or add another certification engine.

Any semantic runtime change requires a separate owning Issue/PR and a fresh release candidate.

## Package boundary

`npm pack --dry-run --json --ignore-scripts` must show only intended distributable content. In particular:

- `skills/refas/` is the runtime/instruction product boundary;
- public schemas are present;
- Python requirements are present;
- both CLI entry points are present;
- physical runtime modules and routed physical contract leaves are present;
- tests, examples, caches, transient project state, ZIP artifacts, and duplicate runtime trees are absent.

## Compatibility

Existing 1.0.x project-state and whole-object-certificate artifacts remain accepted by their public v1 schemas. Runtime 1.1.0 writes the new identity for newly created state/certificates without rewriting existing artifacts in place merely because the package was upgraded.

Physical semantics are additive and opt-in. Assets that only require the established visual reconstruction/certification path do not need runtime binding or a physical-readiness claim.

## Post-merge and publication gate

Merge is allowed only at the exact PR HEAD that passed all required review and CI gates.

After merge:

1. read the exact new `main` SHA;
2. require a successful RefAs CI `push` run for that exact SHA;
3. verify the release workflow consumes that successful main run, not an older candidate;
4. verify `v1.1.0` resolves to that exact `main` SHA;
5. verify the GitHub Release for `v1.1.0` is created or already matches that immutable exact SHA;
6. never move or recreate an existing release tag to hide a defect.

The release workflow is already designed to read the package version from the exact successful main commit and create or verify the immutable matching tag/release. The workflow must remain the source of truth for the publication result.

## Recovery

Pre-release trustworthy baseline: `main@022c442d7725f15982c5776f6330e552ea178e39`, where P17 is closed.

Before publication, recovery is to revert or correct the release-prep change and rerun the exact-head gates. After `v1.1.0` exists, the tag remains immutable; a release defect is corrected by a follow-up patch/minor release rather than retagging 1.1.0.
