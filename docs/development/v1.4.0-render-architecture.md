# RefAs 1.4.0 — CPU rendering architecture (design draft)

Status: DESIGN / NOT IMPLEMENTED. Base: publicly released v1.3.0 at `main@3592883e09b61424131fcd3d2c14029f77232156`. Owner: `rendering`. This is a renderer execution improvement, not a new image-to-3D generator, visual fidelity claim, or change to source-truth authority.

## Problem and current boundaries

- `skills/refas/scripts/render_glb.py` is the portable, deterministic NumPy/Pillow rasterizer; `render_pbr.py` shares its GLB loader, camera and frame utilities and has another per-triangle Python raster loop. Both traverse geometry for each view, creating numerous tiny NumPy scratch arrays.
- `lib/registered-render-replay.mjs` replays only the pinned `RefAs Portable Rasterizer/1.0.0` backend and compares the exact registered hero PNG SHA-256; it imposes a 45-second internal deadline. The current PBR/clay report contract pins the canonical neutral-clay profile and all eight views.
- Tests of >30k triangles use primarily zero-area geometry; the performance test covers only hundreds of nondegenerate triangles. The success of CI does not establish throughput on dense hair meshes or nearly one million live triangles.
- The legacy portable renderer, report serialization, camera convention, frozen source evidence and historical byte replay MUST remain unchanged. The existing public `render`, `render-pbr`, `preview-pbr`, `review-board`, audit/verify/validate commands must continue to work.
- A renderer timeout means rendering/verification is unavailable for that budget, NOT that the asset geometry, source correspondence or appearance has failed. Conversely it cannot authorize a certification PASS.

## Architectural boundary

```text
Immutable input envelope: GLB bytes/SHA, canonical frame bytes/digest,
  backend+algorithm identity, modes/views, output size, lighting,
  color policy, memory/time budget
    |
Trusted render dispatcher (backend selection + capability and budget checks)
    |----------------- legacy portable 1.0.0 (unchanged; historical exact replay)
    |----------------- optimized-cpu v1 (new, optional until qualified)
    |----------------- external adapter (Blender etc.; independently attested)
    |
Backend-specific run in isolated worker -> exact per-view PNG SHA and manifest
    |
Trusted evidence verifier (replay according to recorded backend identity;
  current GLB/camera frozen; capability/feature declarations checked)
    |
Diagnostic / appearance review / certified source-bound gate (separate)
```

The dispatcher's job is **routing**, not certification. Merely selecting a new renderer or having a valid PNG cannot promote a source claim. Preview and proxy results are labeled non-certifying. Existing certified evidence is verified using the algorithm that originally produced it; no implicit re-signing.

## Optimized CPU path: stages

1. **Decode and normalize:** glTF 2.0 accessor/layout validation; explicit unsupported-feature refusal. Normalize node transforms, triangle winding, normals, UVs and primitive IDs to immutable SoA arrays. Keep separate static mesh and instance buffers so repeated meshes need not be decoded repeatedly. Record precise resource consumption, including decoded embedded textures and temporary arrays.
2. **Camera transform:** reuse static world vertices where the scene and GLB SHA match. Transform each vertex once for each camera. Keep near-plane signed distances, not a single "behind" bit. Frustum clip against near plane and image bounds without dropping partially visible triangles.
3. **Visibility setup:** stable, globally ordered (primitive ID, triangle ordinal) triangle setup. Reject truly degenerate triangles, NaN/Inf and outside-frustum triangles. Precompute screen bounding boxes, edge-function coefficients, reciprocal clip-space w and interpolation payload.
4. **Binning:** two-pass screen-tile prefix-sum binning: first count overlaps, then allocate bounded tile indices, then scatter in stable triangle order. Tile lists are read-only during raster execution. Conservative tiles alone do not prove triangle coverage: apply exact edge tests in raster stage. Bound bin explosion by explicit budget and return resource-budget EXCEEDED, not silent triangle truncation.
5. **Compiled raster kernel:** benchmark Numba prototype against C++/Rust CPU implementation on a supported-build matrix before choosing final shipping technology. **No new mandatory native runtime dependency without an optional-package/fallback installation story.** Use predictable SoA loads, fixed top-left pixel-center fill rules, documented near/far clipping, perspective-correct interpolation and stable Z ties. Avoid allocating `np.mgrid` per microtriangle. SIMD is opportunistic and must not change the backend's declared determinism class.
6. **Tile jobs:** disjoint framebuffer regions and local depth/visibility ownership enable multicore execution. Deterministic triangle order and tie-breaking are required regardless of thread scheduling. Bounded per-worker scratch; never mutate shared output from overlapping tile workers.
7. **Visibility/G-buffer:** for repeated *same-camera* modes compute triangle ID/depth/barycentric (and applicable normal/UV) once, then derive portable color, object-ID, albedo and normal passes. Normal/ID/albedo are not a substitute for PBR and shader inputs must be reported. Distinct cameras still require separate visibility.
8. **Shading/output:** compiled or vectorized batches of *visible* pixels, preserve supported material semantics, explicit unimplemented glTF features and color-space policy. Encode PNG and reports deterministically within one backend identity. Stage output and publish the report last, retaining v1.3.0 rollback/digest rules.

## Workload-aware optimization

- First implement instance/primitive frustum culling and screen-space tile binning. A BVH is **conditional**: add it only if measurements demonstrate measurable benefit for large articulated or sparse scene hierarchies, picking or occlusion queries. Rasterization alone does not justify a BVH as a prerequisite.
- Early-Z is already partially present in the current PBR path; keep it and use tile-local hierarchical depth only if correctness on fine strands and overlapping geometry is proved.
- For dense fur, implement explicit subpixel/coverage correctness tests before choosing microtriangle fast paths. Geometry simplification, tuft clustering and LOD are **preview-only by default** and must not certify the original GLB's unchanged silhouette or material representation.
- A preflight must estimate triangle setup cost, tile memberships, decoded texture memory and per-tile scratch; if work cannot fit the caller budget, return a typed BLOCKED outcome and allow a capable external backend, without pretending the asset itself is invalid.
- No automatic "fallback to Blender" inside an accepted canonical report: routing and any change of renderer identity must be recorded and revalidated.

## Non-negotiable invariants

- Canonical input GLB and source bytes are immutable at render time. Camera/axes/source registration remain bound by exact digests.
- Backend identity binds algorithm version, numerical policy, supported features, output settings and replay strategy. The pinned 1.3.0 renderer is retained for its old SHA-256 reports.
- Raw source vs inferred/engineered semantics are unchanged; rendering proves only what the applicable claim scope authorizes.
- Preview/proxy/cache hit is NOT independent visual assessment or source resemblance; failure of one renderer is NOT proof of source mismatch.
- A required certified gate remains fail-closed if no admissible backend evidence exists. Broader backend coverage must be explicitly certified rather than silently relaxing the existing exact replay gate.
- No additional UI-facing validator/checkpoint simply to measure optimization. Favor implementation, benchmark and one accepted high-density vertical slice over breadth.

## Decisions deferred to experiments

Numba vs C++/Rust; baseline tile size (e.g. 16/32/64); SIMD instruction targets and deterministic floating policy; tile overflow/spill strategy; BVH/HZB; exact dense-hair LOD; whether a specific supported external engine can produce eligible canonical neutral-clay evidence. Resolve from actual artifacts, correctness matrices, portability and cost, not assumptions.
