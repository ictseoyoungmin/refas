## Appearance fidelity blocker: the fur is falsely light

The original `PetBed_Fur_mesh` glTF primitive has 512,000 triangles
with a genuine `COLOR_0` accessor. Source **linear vertex colors**
span RGB `[.016076,.003143,.000419]` through
`[.166716,.047669,.010375]`, with approximate mean
`[.081976,.022583,.004759]`. These are clearly not the gray fallback
used by the renderer.

Current `render_glb.load_primitives` ignores `COLOR_0`; the material
`FurMat` omits `baseColorFactor`, which currently falls back to
`[0.7,0.7,0.7]`. Thus the diagnostic `albedo` pass renders the dense fur
**light gray/white instead of its authored brown colors**. This is an
**observed material/appearance limitation**, not a reason to falsify a
geometry-performance PASS. No current diagnostic PNG can certify original
fur appearance, PBR or image resemblance. Material handling needs a separate
versioned, testable fix (no silent acceptance).

## Actual CPU baseline and optimization

Two isolated, local runs used RefAs render scripts SHA-pinned to
`develop/v1.4.0@6ba54bead0773da8c4f52440fb798aa7c8771dd2`,
NumPy 2.3.5 and optional Numba 0.65.1, Python 3.13.5.
`NUMBA_NUM_THREADS=4`, `OPENBLAS_NUM_THREADS=1`, 160×160,
tile32/4 threads, 1024 MiB worker preflight. All timings below are
**same-process warm setup+bin+raster+3-pass shading**, excluding source-GLB
read, JIT compilation and SHA computation. JIT compiled first on
120 genuine synthetic triangle faces; first production-size invocation
may additionally include allocation and cache costs, so the table
compares steady calls #2 and #3 only.

| Renderer | Full scene warm call #2 | Full scene warm call #3 | Median of calls #2–3 |
|---|---:|---:|---:|
| R14-05D before | 795.492 ms | 765.732 ms | **780.612 ms** |
| R14-05E optimized | 384.564 ms | 401.549 ms | **393.0565 ms** |

Observed ratio **~1.99× lower wall-time for this local workload**
(roughly 49.6% less time). This is a **small, noisy local comparison**,
not a cross-hardware claim or production SLA. Old `_setup` allocated
`polygon`, `clipped`, `vertices`, `rgb` per triangle/fan and copied
a row on negative winding; the candidate now allocates those temporary
arrays once per **sequential invocation** and performs an in-place
three-scalar row swap. No shared static state or thread races.
Persistent 2× raster-setup storage and memory-budget policy are **unchanged**.

Representative stages in production warm call #3, ms:

| Stage | Old | Candidate |
|---|---:|---:|
| `_setup` | 458.210 | **246.263** |
| Binning | 31.963 | 30.162 |
| Raster | 213.253 | 65.911 |
| Whole 3-pass | 765.732 | **401.549** |

The raster-stage change may reflect runner scheduling and memory effects,
not a raster algorithm modification; only the per-triangle setup allocation
was intentionally optimized. Do not attribute all elapsed change to setup
without repeated controlled runs.

## Exact QA against the *actual* source GLB

**14/14 paired test settings** across old and optimized renderer produced
bit-identical Normal, Object-ID, Albedo RGB arrays and float64 depth/int64
winner buffers, verified by SHA-256 (not IoU) with the **same GLB SHA and
provisional camera frame SHA**. Settings include:

- Three whole-model 160px repeats and 8 alternate 16/32/64 tile
  × 1/2/4 worker configurations.
- Real unmodified **fur-only** primitive selection
  (512,000 triangles), and real **non-fur** primitive selection
  (389,664 triangles); these are *separate diagnostic views*, not
  a decimated substitute or additive timing decomposition.
- Whole-model 384px rendering, still exact SHA parity.
- All 901,664 original indexed faces prepared in full-scene passes,
  **0 reported input geometry omissions**, with 160px
  `coveredPixels=4808` and 384px `coveredPixels=27937`.

In the original warm local run, the isolated fur render took
448.083 ms and non-fur primitives took 249.077 ms;
the optimized counterparts took **216.269 ms** and **171.657 ms**.
These timings cannot be summed to reconstruct the composite render because
occlusion and tile membership differ.

Old run cumulative process `VmHWM` reached **626,824 KiB**;
candidate run reached **625,928 KiB**, including JIT, GLB parsing and
temporary allocations. `VmHWM` is not per-call isolated peak RSS.
