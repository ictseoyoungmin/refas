# R14-00 — Portable CPU renderer baseline instrumentation

Status: IMPLEMENTED candidate; measurements are diagnostic, not certification. Uses the installed v1.3.0 `render_glb.py` algorithm unchanged. Read the confirmed CI and actual run reports before claiming any runtime performance improvement.

## Run

```bash
# Fast smoke: single registered hero view, organic positive-area triangles
python3 skills/refas/scripts/benchmark_render_cpu.py \
  --case organic --triangles 1000 --views hero --size 64 \
  --repeats 3 --out temp/bench-organic-1k.json

# Dense hair-like ribbons with overlapping, subpixel genuine triangles
python3 skills/refas/scripts/benchmark_render_cpu.py \
  --case strands --triangles 10000 --views hero --size 96 \
  --timeout-seconds 180 --max-working-mb 512 --repeats 3 \
  --out temp/bench-strands-10k.json

# Generate exactly 1,000,000 positive-area strands triangles, no expensive rendering
python3 skills/refas/scripts/benchmark_render_cpu.py \
  --case strands --triangles 1000000 --dry-run --save-fixture temp/r14-1m \
  --out temp/bench-1m-mesh-preflight.json

# Actual 1M rendering: execute only on a provisioned CPU runner; costly and bounded.
python3 skills/refas/scripts/benchmark_render_cpu.py \
  --glb temp/r14-1m/benchmark.glb --frame temp/r14-1m/frame.json \
  --views hero --size 160 --timeout-seconds 600 --max-working-mb 1024 \
  --repeats 3 --out temp/bench-strands-1m.json

# Canonical eight-view cost on a smaller real workload
python3 skills/refas/scripts/benchmark_render_cpu.py \
  --case hard-surface --triangles 10000 --views eight --size 96 \
  --repeats 3 --timeout-seconds 240 --out temp/bench-hard-10k-8.json
```

Use `--glb existing.glb --frame canonical-frame.json` for a real production asset; synthetic workloads never certify source appearance. Retain provided GLB/frame SHA and machine details when comparing runs. `--save-fixture` can retain source bytes needed to replay a generated run, since temp fixture directories are removed by default.

## Recorded fields

- `schema: refas.cpu-render-benchmark/v1` and `claimScope: measurement-only`;
- source GLB SHA-256 and byte size, canonical frame SHA-256;
- requested/actual triangles, generated-workload type and seed; sampled strictly positive triangle area;
- Python/Numpy/platform/CPU logical count, resolution, tile setting, memory/timeout limits;
- per-run wall time, Linux process peak RSS (or nullable unavailable), typed status, failure excerpt;
- parsed GLB, resource preflight, world transform/decode and frame setup durations;
- each selected view's combined raster/shade/PNG encode time, covered pixel count, rendered triangles and PNG SHA-256.

The baseline **cannot separately time** triangle setup, rasterization, shading and PNG encoding within `render_glb.render` without intruding into its pinned code. These are explicitly reported as a combined stage, not fabricated independent values. The first compiled kernel slice will expose the finer-grained timers. VMHWM is a process memory observation, not an exact allocation census. Cold/warm page-cache effects are not guaranteed by repeats; report them as distinct only if measured under explicit conditions.

## Limits and CI policy

Default PR CI exercises only 502 organic triangles and 1201 strand-triangle fixture generation, plus an explicit bounded-memory error. The 10k/100k/500k/1M experiments are on-demand and should use pinned CPU/hardware, seeds, camera and budgets. Three or more repeats give a median and min/max; numeric performance SLAs are selected only after comparable baseline runs.

A timeout, budget refusal or unavailable worker is a `BLOCKED_*` measurement result, **not** evidence of broken model geometry. An opaque PNG proves only that the current backend rendered; no source-fidelity authority is created. The pinned legacy renderer, its exact PNG digests and strict trusted replay stay unchanged.
