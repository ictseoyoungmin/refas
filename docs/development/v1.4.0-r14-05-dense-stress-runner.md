# R14-05C — Dedicated dense-mesh CPU stress on real GLB triangles

Status: IMPLEMENTATION CANDIDATE. This is measurement infrastructure, not an
R14-05 throughput or source-fidelity closure. The benchmark is deliberately
absent from regular Node20/22/24 PR and develop CI.

The first executed stress result (100k, 500k, 1M; all COMPLETE) is retained
as [measured evidence](v1.4.0-r14-05-measured-2026-10-15.md).

## Isolated GitHub Actions invocation

The workflow `.github/workflows/r14-05-dense-benchmark.yml` triggers **only**
on explicit `bench/r14-05-*` branch pushes (or workflow_dispatch once a
workflow file exists on the default branch). It never triggers on ordinary
`develop/v1.4.0`, `main`, or feature PR commits.

After its implementation is merged into develop, start one test by creating
a new `bench/r14-05-YYYYMMDD` branch at the exact reviewed develop commit
and committing a small marker file. Run the workflow on the marker's commit
and preserve its exact SHA in the evidence summary. Do not create the branch
from a different head without recording the difference.

The isolated job matrix creates seeded, **positive-area** fur-ribbon GLB
fixtures of 100k, 500k, 1M triangles, plus canonical Hero frame. All use
160×160 resolution, tile 32, four Numba threads and a declared 1024 MiB
worker preflight on Ubuntu 24.04/Python 3.12/Numba 0.65.1.

| Real triangles | Fresh-process cold-JIT repeats | Per-run timeout |
|---:|---:|---:|
| 100,000 | 3 | 540 s |
| 500,000 | 2 | 540 s |
| 1,000,000 | 1 | 540 s |

The workflow uploads one immutable report artifact per triangle count for
30 days regardless of success/failure. The fixture source GLB SHA, generator
and seed are recorded. Synthetic GLBs are useful throughput fixtures but
do **not** demonstrate accuracy against a supplied Monster Bed or image.

## Benchmark report trust and interpretation

`benchmark_render_cpu_dense.py` runs a new CLI subprocess for each repeat
(no visibility disk cache), and captures real wall time, Python/NumPy/Numba
versions, OS/platform, OS-reported CPU model/core count, and sampled Linux
peak RSS. It independently verifies that the renderer wrote all three
normal/object-ID/albedo PNG files, each on-disk image matches its reported
SHA-256, the report is diagnostic-only, GLB/frame SHA match requested bytes,
and the renderer profile matches the currently installed worker.
Missing/modified outputs result in `FAILED_BACKEND`; budgets/timeouts are
reported as blocked, **not a defective 3D asset**.

Do not compare these elapsed times directly to an unrelated shader/PBR
backend or call them normal three-pass performance gains. Every repeat is a
fresh worker and includes **cold Numba compilation**, not a warmed JIT kernel.
The matrix spans different runner CPUs unless explicitly pinned; report
CPU model and do not calculate platform-independent speedup.

If one case fails because of time/resource constraints, keep the typed
artifact and identify which stage failed. Do not remove the case or treat
it as PASS. On-demand data helps select optimizations for R14-05D.

## Still required to close R14-05

- Actual supplied production GLB with matching registered canonical frame,
  including Monster Bed if available (not discovered in this project files).
- Warm-JIT/kernel-only 100k/500k/1M results on pinned hardware alongside
  subprocess cold-JIT results; 1/2/4/8 thread and tile-size matrix.
- Memory accounting including decoded geometry, JIT and intermediate buffer
  peaks, malformed source/timeout cases; source and output SHA retention.
- Canonical-view production quality and registered replay remain separate
  R14-06+ authority gates. No automatic promotion from benchmark results.
