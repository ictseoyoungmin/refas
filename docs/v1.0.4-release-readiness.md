# RefAs 1.0.4 release readiness

RefAs 1.0.4 is release-ready only when the exact candidate commit passes the normal pull-request CI matrix and the protected Node 24 dogfood/release-audit chain. This document adds the Host Integration release boundary to the existing Core release criteria; it does not weaken earlier reconstruction, evidence, fitting, assembly, visual-review, relational-authority, or certification requirements.

## Host Integration contracts

The distributable package must contain and validate these public contracts:

- `refas.host-session/v1`
- `refas.host-event/v1`
- `refas.host-operation/v1`
- `refas.host-review-bundle/v1`
- `refas.artifact-handoff/v1`
- `refas.worker-request/v1`
- `refas.worker-response/v1`

Host persistence remains private. External hosts must consume public APIs or the `refas-host` companion CLI instead of reading `.refas/` directly.

## Authority preservation

Release readiness requires all of the following:

- host session/status is a projection over RefAs state rather than a competing reconstruction state machine;
- durable host-event sequence remains monotonic, replayable, and fail-closed on tampering;
- pause and cancel remain distinct and cancellation reuses existing bounded-edit rollback authority;
- review bundles remain presentation envelopes and cannot pass review, resolve findings, or certify;
- artifact handoff binds the exact current GLB/checkpoint/transaction/certification state and cannot certify by itself;
- workers cannot emit durable host events, mutate host state, certify, roll back, or self-declare timeout/cancellation/failure authority;
- stdout is worker protocol only, stderr is diagnostics only, and returned artifact bytes are reverified by the parent;
- product-specific UI states and hidden reasoning are absent from public RefAs contracts.

## Recovery hardening

A host state created immediately before process loss may exist with sequence `0` and no events. Reopening that pristine state must repair exactly one `session-opened` event and must not duplicate it on later opens. States that already contain event or operation history are never rewritten into a new session-opened history.

## Distribution and CLI

The package must expose both `refas` and `refas-host`. The companion CLI must support stable host open/status, durable event replay in JSON/JSONL form, polling follow mode by event sequence, review-bundle inspection/publication, exact artifact handoff/currentness checking, and worker request/response validation.

`npm pack --dry-run --json --ignore-scripts` must include the Host Integration reference leaf, companion CLI, public runtime modules, and public schemas. It must still exclude tests, examples, transient state, caches, archives, and duplicate runtime trees.

## Exact-head proof

Before merge, the PR head must pass:

- Node 20/22/24 JavaScript regression tests;
- Python syntax gate;
- installed-skill instruction-boundary audit;
- semantic instruction-graph audit;
- repository/product-boundary audit;
- complete reconstruction dogfood;
- joint parameter-fit dogfood;
- independent PBR dogfood;
- hard-surface topology dogfood;
- modular assembly contact dogfood;
- release audit and npm package dry-run.

Any source change after this proof requires a new exact-head CI run.

## Publication boundary

Merging the 1.0.4 release-hardening change does **not** authorize package publication, a Git tag, or a GitHub Release. The `v1.0.4` tag and GitHub Release are a separate protected action and must be explicitly authorized after the final `main` commit and its post-merge state are inspected. Existing tags remain immutable.
