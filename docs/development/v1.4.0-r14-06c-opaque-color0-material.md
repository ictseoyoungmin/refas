# R14-06C1 — Visible-only opaque COLOR_0 material preview

Status: **implementation candidate**; this is deliberately a small material
slice, **NOT** yet trusted PBR evidence or full-source resemblance.

## Architecture and actual code

`skills/refas/scripts/render_pbr_v2_material.py` consumes
`render_pbr_v2_visibility.render_visibility` once per camera and only shades
the *winning visible samples*, using stable original triangle IDs and
perspective-correct source barycentric weights. It **does not alter** v1's
`render_pbr.py`, historical R04 Neutral Clay profile, v1 PBR schema
or v1 trusted replay.

The source scene is loaded **once**, and primitive/material binding is
recreated by walking the original glTF scene nodes/mesh primitives in
their actual order. This avoids assigning colors based on guesses or
flattened source filenames. Opaque per-pixel base color is:

```text
linear RGB = original glTF material.baseColorFactor (default white)
           × sum_k (source-barycentric-weight[k] × COLOR_0[original vertex[k]])

display albedo = IEC 61966-2-1 sRGB OETF(linear RGB)
```

The CLI provides four **material previews**, sharing one visibility
surface: `albedo`, `normal`, `object-id`, `beauty`. Normal and
Beauty interpolate true original per-vertex normals/positions at visible
fragments. Beauty is fixed *direct-light*, metallic/roughness approximate
Cook–Torrance, with **no IBL**, normal-map, multi-bounce, shadows or
GI. It is *not* physically complete glTF PBR certification.
Other material-input paths are deliberately blocked with
`PBR_V2_UNSUPPORTED_MATERIAL`: baseColorTexture/samplers (until
linear-space bilinear and mip contracts are implemented), alpha MASK/BLEND,
emissive, occlusion maps, normal maps, unimplemented extensions,
non-triangle/morph and vertex alpha not fully opaque.
These must never silently become a flat material fallback.

The v2 path uses spec-correct glTF baseColorFactor defaults **without
changing v1 legacy fallback semantics**: 1.0 for absent RGB factor,
metallicFactor=1.0 and roughnessFactor=1.0.
All material features are checked **before** the expensive compiled
visibility stage. Geometry-only R14-06B may remain available when a
material preview is blocked.

## Interface and trust

Diagnostic CLI only:

```bash
NUMBA_NUM_THREADS=4 python3 skills/refas/scripts/render_pbr_v2_material.py \
 --glb monster_bed_v4.glb --frame diagnostic-frame.json \
 --out temp/monster-r14-06c --size 160 --tile-size 32 \
 --threads 4 --max-working-mb 1024
```

Output: separate SHA-256-bound PNGs and `preview-report.json`,
schema `refas.pbr-v2-material-preview/v1`,
`claimScope=material-preview-only`, `certificationEligible=false`.
Report records full input GLB SHA, camera-file SHA, visibility depth,
source winner and barycentric digests, stage time/coverage and
required-versus-unsupported feature list. Output directory cannot
exist prior to publication. Preview files are staged and published
only after every requested pass succeeds.

No user-uploaded GLB or camera proxy may be inserted in the public
repository. Temporary AABB camera is NOT trusted source registration.

## Focused acceptance

`tests/test_render_pbr_v2_material.py` provides a separately calculated
pixel-level COLOR_0 × factor × sRGB oracle, transfer inverse, occlusion,
deterministic tile parity, and unsupported texture, normal-map, alpha
refusals. It also executes a real, tiny indexed GLB through the worker
and re-hashes all outputs, ensuring no false certification bits.

The full Monster Bed has **901,664 original triangles** and 512,000
fur triangles with 320,000 original COLOR_0 vertices. The R14-06D
production workload acceptance remains separate until the entire
original GLB and corresponding AABB-only *provisional* diagnostic camera
are run against the new material worker with measured wall time and
RSS; test it externally/locally, not in ordinary PR CI.
