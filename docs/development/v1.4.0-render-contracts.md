# RefAs 1.4.0 — renderer contracts and verification (design draft)

Status: DESIGN / no new runtime API yet. Existing v1.3.0 schemas and legacy renderer outputs remain authoritative until an explicit migration has passed all trust gates.

## A. Proposed job input (`refas.render-job/v1`)

```json
{
  "schema": "refas.render-job/v1",
  "asset": {"path": "candidate.glb", "sha256": "<sha256>"},
  "frame": {"path": "canonical-frame.json", "sha256": "<sha256>", "frameDigest": "<sha256>"},
  "backend": {"id": "optimized-cpu", "algorithmVersion": "1", "profile": "diagnostic"},
  "views": ["hero", "side"],
  "resolution": [512, 512],
  "passes": ["beauty", "normal", "object-id", "albedo"],
  "lightingProfile": "neutral-clay-three-light-v1",
  "resources": {"wallSeconds": 180, "workingMiB": 512, "threads": 4},
  "intent": "preview"
}
```

This is a **proposed** envelope, not a promise that a new backend can currently render every mode. Source registration, appearance/neutral-clay presets, color policy and exact per-view camera values are resolved by a trusted dispatcher; user-provided `backend.id` is never proof of a trusted implementation. Do not embed the placeholder digest above into real fixtures.

## B. Output and typed result

Minimum proposed result: `refas.render-execution/v1` with immutable requested input digest, actual GLB/frame SHA, selected backend ID/version/executable hash (or environment identity), deterministic policy, supported and unsupported glTF features, view/camera metadata, per-PNG SHA, stage time (decode/transform/setup/bin/raster/shade/encode), peak RSS, memory-budget estimate, elapsed wall time, failed stage (if any), and the independently determined `claimScope`.

Operational outcomes (distinct from certification):
- `COMPLETE`: genuine source-GLB views rendered; certifying only after applicable replay/visual-review gate.
- `BLOCKED_UNSUPPORTED`: material/extension/raster rule unsupported by this backend.
- `BLOCKED_RESOURCE`: memory, tiling or compute budget exceeded.
- `BLOCKED_TIMEOUT`: deadline hit, including replay deadline.
- `FAILED_ASSET`: malformed, invalid/unreadable GLB or invalid camera input.
- `FAILED_BACKEND`: crash, non-deterministic failure, internal error or mismatched replay.
- `INCOMPLETE`: missing views, truncated output, stale/tampered artifacts or interrupted commit.

The project-owned QA outcome stays `PASS / FAIL / INSUFFICIENT` under existing contracts. In particular, `BLOCKED_* ` maps to **insufficient rendering evidence**, never to positive resemblance nor automatically to invalid geometry. Preserve typed causal diagnostics in machine-readable output.

## C. Backend trust and replay

Proposed `refas.renderer-backend-profile/v1` registry is **trusted code/config**, not worker-supplied arbitrary JSON. It records:
- Stable `id`, `algorithmVersion`, `kind` (`legacy-cpu`, `optimized-cpu`, `external`), binary digest/installation provenance and allowed command line.
- Supported passes, glTF material/geometry coverage, deterministic/replay policy and platform constraints; resource controls and exit codes.
- Admissible `claimScope` per profile: `preview-only`, `render-integrity-only`, `shape-resemblance-only`, `visual-fidelity`. These are **maximum possible scopes**, not automatic assertions.
- A trusted replay verifier or separately implemented render attestor; outputs must be bound to exact GLB/frame/camera bytes, not simply the command invoked.

**Legacy v1.3.0:** retain `render_glb.py`, exact identity `RefAs Portable Rasterizer/1.0.0`, its published PNG-byte digest algorithm and existing `registered-render-replay.mjs` when verifying old work. Do not reinterpret old PNG digests under a new SIMD math implementation.

**Optimized CPU:** use a **different** renderer identity. Exact SHA replay within its pinned implementation/build when feasible; otherwise a formally bounded cross-hardware nondeterministic contract is limited to explicitly permitted visual/diagnostic contexts. A tolerance comparison cannot quietly replace strict original registered-hero provenance. Divergence requires `INSUFFICIENT` or an independently validated new trust path.

**External engines:** e.g. separately installed Blender/Eevee/Cycles. Capture exact executable/engine version, GLB import settings, frozen camera, exact scene/lighting/color config, output digest and process exit; do not assume their images prove source alignment. First implement a single real adapter end-to-end, not a family of name-only adapters. External renderer execution in a new process is not by itself independent **implementation verification**.

**Neutral clay:** v1.3.0 canonical `refas-neutral-clay-v1` and `NEUTRAL_CLAY_RENDERER_PROFILE` are pinned to the bundled PBR profile and 8 views. Never relabel an optimized/Blender render as that legacy profile. A new permitted neutral-clay backend requires an explicit new preset/profile, evaluator update and adversarial parity/replay tests.

## D. Cache keys and provenance

Separate layers with exact keys and invalidation:
- `Decode`: GLB SHA + glTF decoder/normalizer version.
- `World`: decode key + instance transforms + scene selection.
- `Camera/setup`: world key + canonical frame SHA/digest + camera parameters + clip/raster policy + selected view.
- `Visibility`: setup key + backend algorithm/build identity + resolution + MSAA/sample/depth/tie policy + geometry/material alpha rules.
- `Shading`: visibility key + material/texture digests + light rig, exposure, color pipeline + pass.
- `Output`: shading key + PNG encoder/build and output format.

Caches are **derived aids**: an exact digest chain and immutable keys are required on every reuse; rejecting stale/tampered entries is correct. An in-memory cache may accelerate passes; a disk cache must be content-addressed, size bounded, atomic on publish, and disposed using reference-aware retention. Never use a cached preview as a canonical 8-view or independent material report.

## E. Raster correctness matrix (goldens + invariants)

For each backend record algorithm/camera/float profiles and test:
- near-plane crossing, partially offscreen triangles, large clipped triangles; depth/ordering with equal depth, shared edges and thin slivers;
- winding and negative scale, perspective-correct UV, mirrored instances, nonuniform normals, transparent/alpha-tested material refusal or correct handling;
- small and large triangles, dense tufts with overlapping depth layers, repeated identical meshes, missing/unsupported glTF extensions;
- 1/2/4/8 threads and multiple tile sizes: exact pixel SHA for deterministic profiles, otherwise rigorously bounded explicitly supported metrics;
- GLB corruption, hostile accessor ranges, decompression/texture bombs, huge bin membership, over-budget RSS, cancellation and timeout;
- image/report tampering, cache poisoning, wrong frame/renderer identity, stale GLB, replay spoof and missing output: must fail closed;
- reproducibility on declared CPU architectures and Node/Python/optional-native installation matrix.

Golden images are **per backend version** and do not retroactively change the v1.3.0 images. Change in raster-fill rules or math requires versioned goldens and explicit transition.

## F. Migration sequence and public compatibility

1. Register legacy profile without changing the strict old replay's assertions.
2. Introduce new envelope/dispatcher as additive opt-in API, still writing existing public reports only when their native schema/evaluator genuinely accepts them.
3. Validate optimized backend independently; preserve existing `refas render` default until measured, review-approved and the new authorized replay path exists.
4. Add trusted profile selection with explicit feature/budget refusal and no misleading silent fallback. Maintain legacy CLI aliases and plugin discoveries.
5. Integrate one external adapter if it can preserve GLB/frame provenance and source-bound gate semantics.
6. Release 1.4.0 only when current/old replay, installed distribution, source/visual gate tests, and dense-mesh acceptance all pass. No automatic claims about improved reconstructed shapes.

Compatibility is an executable property of real old projects and PNG digests, not just matching JSON schema names.
