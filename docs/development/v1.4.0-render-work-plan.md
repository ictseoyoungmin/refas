# RefAs 1.4.0 — CPU renderer implementation slices and acceptance

Status: DESIGN. Base commit `3592883e09b61424131fcd3d2c14029f77232156`; active development branch `develop/v1.4.0`. Keep `main`, release tag v1.3.0, `package.json` and public plugin version at 1.3.0 until release promotion. Do not alter the installed skill's agent-facing guidance until the corresponding runtime command exists.

## Development method

Implement one **measurable vertical slice** before widening backend support. Each slice is its own PR/commit to `develop/v1.4.0` with tests; run Node 20/22/24 CI and focused render/correctness tests on every PR. Keep the retired multi-minute `npm run dogfood` scene workflow **manual-only**; it is not part of regular CI or weekly Deep QA. Focused regression tests and scoped render integrity checks continue in CI; milestone `[full-qa]` pushes and release candidates run targeted scene, PBR, compatibility and release-audit checks instead. The v1.4.0 release publisher's existing v1.3.0 requirement for the old `Complete dogfood` job step must be revised at R14-08 to use the new verified QA step set. A changed raster algorithm that affects evidence or camera coordinates reopens the relevant previously closed correctness and certification checks.

### R14-00 — Current implementation benchmark and policy baseline (first)

Deliverables: source-pinned baseline from v1.3.0, real nondegenerate workload generator, optional supplied GLB test hook and repeatable measurements: 1k/10k/100k/500k/1M triangles; scene types hard-surface, organic and dense strand/tuft; one registered hero and 8-view runs at multiple sizes. Record reference inputs by SHA, counts of actually setup/rasterized/visible triangles, elapsed and individual stage timing, peak RSS, output PNG SHA, hardware cores/ISA and backend version. Record warm/cold results separately; 3 or more repeats, median and spread. No user image is needed to fabricate a benchmark subject; synthetic **geometry** is allowed for workload tests, while reference resemblance claims require real evidence.

**Gate:** benchmark produces honest failures/timeouts and distinguishes invalid asset vs resource vs backend limitations. Explicitly reproduce the existing small-test/30k degenerate-test limitation. Select post-baseline throughput and budget targets; do not publish invented speedups.

### R14-01 — Backend identity and dispatcher

Add internal `RenderJob` / `RenderExecution` normalization, trusted profile registry, typed blocked causes, digest-bound input and output identity, legacy adapter. The new optimized backend is **not yet enabled for certification**. Keep published CLIs and exact SHA replay unchanged.

Initial implementation: `skills/refas/scripts/lib/render-backend.mjs` is an internal-only opt-in adapter. It supports one legacy diagnostic hero with fresh output directory, frozen SHA-checked GLB/frame, typed budget/unsupported error and verified PNG hash. `optimized-cpu` is registered as unavailable and cannot silently fall back. Installed certification replay remains the existing unmodified `registered-render-replay.mjs`; an output from the new diagnostic adapter is explicitly **not** a registered-replay certificate. R14-02 will add the actual compiled backend.

**Gate:** wrong/missing backend, swapped GLB/frame/PNG, forged profile or reused cached preview cannot pass; old v1.3.0 projects and replay still pass.

### R14-02 — Compiled CPU raster vertical slice

Prototype a 1-view `normal`/`object-id` pass for one mesh class with top-left fill, near clipping, stable depth tie, deterministic order and bounded allocations. Compare Numba vs C++/Rust with repeatable workload and installed-package constraints; choose one implementation, with graceful portable fallback. No requirement to buy into all glTF extensions at this stage.

**Current candidate:** `skills/refas/scripts/render_cpu_opt.py` implements an optional serial `numba==0.65.1` JIT prototype using the same public GLB loader, frozen Hero camera and new normal/object-ID-only raster rules. It supports near-plane clipping, a versioned top-left rule and stable depth priority; rejects textures, skinning, morph targets and unsupported materials. The R14-01 dispatcher now exposes the prototype opt-in as `optimized-cpu` with explicit pass selection, distinct `RefAs Optimized CPU/1.0.0-jit-prototype` identity and no certification permission. Numba is NOT a standard install dependency; a missing wheel yields `BLOCKED_UNSUPPORTED`. GPU, parallel tile binning, complete PBR, cache and an independently admissible replay remain future work. Speed and resource limits must be measured; the initial runtime prototype does not establish a 1M-triangle 10-minute SLA.


**Gate:** golden outputs and adversarial raster correctness; visual coverage matches declared policy; real nondegenerate throughput and memory profile measured; unsupported features rejected explicitly.

### R14-03 — Binned multithreaded raster and culling


**Current implementation candidate:** `render_cpu_tiled.py` introduces a separate `tiled-cpu` diagnostic backend with near-clip and screen-space triangle setup, stable two-pass tile counts/prefix-sum/scatter, bounded bin entries, and disjoint per-tile Numba `prange` workers. Output is scoped to a registered hero camera and opaque Normal/Object-ID only, with explicit `tileSize=16/32/64` and `threads=1/2/4/8` inputs. The existing R14-02 serial JIT worker remains separate, unchanged and independently identifiable. A dedicated test matrix compares exact pixel/depth/winner buffers across supported threads and tile sizes, including near-plane clipping, overlapping strands, depth ties and typed resource refusal. The optimized worker is **not** enabled for certification; neither its preview nor benchmark timings imply visual resemblance. Primitive-level BVH/HZB, general glTF material support and certified 8-view/PBR remain unimplemented; real CPU scaling is to be measured after the correctness gate.



Add screen-tile prefix-sum binning, primitive frustum culling, bounded bin occupancy, disjoint tile workers and CPU core scaling. Compare 1/2/4/8 workers, 16/32/64 tile sizes, disjoint output hash equality and peak memory. BVH/HZB enters only on measured benefit.

**Gate:** race/overflow/ordering/cancellation fault injection; output independent of thread count for the new deterministic profile; >=100k actual nondegenerate triangles profiled.

### R14-04 — Pass sharing and layer-specific caches

Initial implementation candidate: `render_cpu_visibility.py` derives Normal/Object-ID/opaque Albedo from one R14-03 hero visibility/depth raster and optional SHA/version-scoped non-pickle diagnostic disk buffers, with refuse-on-tamper behavior. This is additive to the unchanged standalone R14-02/R14-03 APIs and DOES NOT enter the independent certifying replay path. Tests include same-camera pass parity, cache hit/miss, frame change invalidation, buffer tampering, overlap geometry and PNG digest correctness. [Runtime usage and known limitations](v1.4.0-r14-04-visibility-cache.md).


Shared same-camera visibility for beauty/normal/object-ID/albedo; exact input/version keys; staged content-addressed optional caches; scope-local invalidation and poisoning/rollback tests.

**Gate:** cached and uncached outputs match the new backend goldens; memory ceiling respected; source/profile change cannot reuse prior cache; separate cameras cannot share a visibility buffer.

### R14-05 — High-density strand and microtriangle handling

linear per-vertex colors are no longer discarded by the GLB loader;
the independent PBR path now uses perspective-correct interpolation,
material-factor multiplication and sRGB output. The CPU diagnostic
Albedo and portable flat-color Beauty/Albedo instead **fail closed**
rather than falsely displaying uniform gray, while geometry diagnostics
stay accessible. See
[COLOR_0 material contract](v1.4.0-r14-05f-color0-material.md).
Full multiview source-registration/PBR certification remains OPEN.

R14-05E candidate: genuine user Monster Bed GLB (SHA-256
`30f8e135a34470366780b9b600040dff823171dfe857e7e4ab681c520a95f8d7`)
with all **901,664 indexed triangles** decoded and measured using a
clearly non-authoritative bounding-box camera. The renderer's per-triangle
small scratch array allocations were replaced by **per-call sequential
scratch reuse**: local steady 160px same-process measurements improved
from ~780.6 ms to ~393.1 ms, with **14/14** exact old/new
Normal/Object-ID/Albedo + depth/winner SHA parity comparisons over real

This is a local, provisional-camera diagnostic result, **not a certified
Hero/source-resemblance outcome**. The original fur uses 512k COLOR_0

## Acceptance dashboard (initial targets / to refine after R14-00)

| Dimension | Required proof |
|---|---|
| Compatibility | Bit-identical existing 1.3.0 legacy reports and trusted hero replay under legacy identity |
| Correctness | Defined clipping/tie/interpolation rules, per-backend goldens and multi-core parity |
| Safety | Bounded RSS/scratch/bin capacity, typed timeout/unsupported/resource outcomes, fail-closed certification |
| Performance | Workload-pinned comparable timings for 10k–1M **nondegenerate** geometry, peak RSS, CPU/hardware disclosure; numerical SLA set only after baseline |
| Scope | Portable diagnostic, neutral-clay, PBR and external feature support declared individually, not inferred from a family name |
| Packaging | Real package install, no implicit native dependency, platform matrix and skill operation discovery |
| QA efficiency | Focused PR tests, tagged deeper benchmarks, exact release candidate full QA; avoid recurrent multi-minute CI on every PR |

## Not in scope

Rewriting observation/source semantics, adding new certification authorities, changing the canonical v1.3.0 neutral-clay contract in place, claiming automatic fidelity gains, broad glTF feature support without real coverage, multi-backend framework scaffolding without a working render vertical slice, artificial high-performance results from degenerate triangles.

## Order and state

`R14-00 -> R14-01 -> R14-02 -> R14-03 -> R14-04 -> R14-05 -> R14-06 -> R14-07 -> R14-08`.

Revisit this order **only** if the first benchmark shows a different dominant cost. Prioritize useful measured rendering, not ceremony. Only R14-00 planning is authorized by this design commit; the runtime remains unchanged until implementation PRs.
