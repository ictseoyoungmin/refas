# R14-06A design candidate — Independent PBR v2 rearchitecture

**Status: DESIGN ONLY / NOT IMPLEMENTED.** Base: `develop/v1.4.0@ced41b4aec14b83d22511b9f221af3c8a3ca4c92`. This proposal must not modify the existing v1 renderer/report, introduce a new certified identity, or close R14-05 / #364 by writing a design document.

## 1. Evidence and why another local optimization is insufficient

Current bundled `skills/refas/scripts/render_pbr.py`:

- Python iterates every triangle, constructs an `(3,2)` screen array, recomputes per-triangle UV and bounded NumPy `mgrid` arrays, then performs edge, depth, interpolation and shading inside nested Python tile loops. Bounded scratch is helpful but avoids neither Python loop overhead nor repeated allocation.
- It has **no bin-and-scatter per-tile primitive lists**, no compiled visibility kernel, and no reusable winner/depth plus per-fragment interpolation data. Every pass/view launches the full triangle loop; the all-eight-view canonical path runs serially.
- If **any** of a triangle's depths is `<= 0.01`, the triangle is silently discarded. Near-plane crossing is not clipped, so material/PBR output can omit valid visible fragments. The Numba diagnostic backend and the independent PBR do not currently have identical geometric coverage.
- `COLOR_0` source color now receives a piecewise sRGB output transform; other albedo/PBR colors still use an approximate power 1/2.2 transform. Embedded texture filtering happens on sRGB values before decode, while the glTF spec expects interpolation in linear RGB. The shader also lacks several glTF surface features and must not broadly assert material completeness.
- An opaque, unchanged user-owned `monster_bed_v4.glb` has **901,664 original triangles / 512,000 fur triangles / 320,000 COLOR_0 fur vertices**. The bundled independent PBR could not finish a complete fur-only raster within 150 seconds of local test; no full-asset PNG or source-resemblance proof was obtained. A sparse 8,000 *original face* COLOR_0 experiment validated interpolation but is not a production renderer acceptance test.
- Current `refas.pbr-render-report/v1` binds source/scene/renderer/lighting/output digests and checks an independent process, but **a report digest is not a proof of pixel correctness**. The v1 canonical neutral-clay identity and its exact profile/digests are pinned in `pbr-render-report.mjs`. Silent in-place replacement would invalidate or misrepresent historical evidence.

**Decision proposed:** build a separately identified independent PBR v2 worker and an independently verifiable external engine adapter. Reuse source parsing and proof conventions as appropriate, but do not label a shared diagnostic raster as independent visual validation. Preserve v1 replay and pinned neutral-clay outputs.

## 2. Architecture and responsibility boundaries

```text
Unmodified GLB + verified frame + source reference + quality intent
                           |
               [ A. Frozen input / preflight ]
               asset/frame SHA, geometry/attribute inventory,
               per-feature material support, budget, job policy
                           |
               [ B. PreparedScene (immutable SoA) ]
               positions, indices, normal/tangent, COLOR_0, UVs,
               materials/textures, original triangle + primitive IDs
                           |
               [ C. per-view clip, project, bin ]
               near/frustum clipping, preserve triangle provenance,
               conservative tile ranges, compact deterministic bins
                           |
               [ D. tiled visibility / ownership ]
               depth + top-left + tie rules + winning primitive/triangle
               + perspective interpolation provenance
                           |
               [ E. shade visible samples only ]
               linear vertex color x factor x linear texture,
               normal/tangent, metallic-roughness BRDF + controlled lights,
               optional alpha/mask path only when validated
                           |
               [ F. explicit color/output transform ]
               scene-linear -> pinned exposure/tone map -> sRGB,
               normals/object-IDs/clay/albedo + beauty where eligible
                           |
               [ G. source-bound output report/publisher ]
               staging, PNG hashes, provenance, independent gate checks,
               atomic manifest publication, typed refusal
                           |
              +------------+-------------+
              |                          |
        bundled CPU fallback       external trusted engine
        (Numba optional)           (distinct importer and renderer)
        deterministic QA           independent appearance cross-check
        not certification alone    still needs independent acceptance
```

### A. Intake and feature inventory
- Freeze GLB/frame bytes *before* rendering; validate their hashes and reject after-read changes. Derive a **required material-feature inventory from the source GLB** (COLOR_0, texture coordinate sets, alpha mode, doubleSided, normal maps, metallic-roughness texture, emissive, extensions, skinning, morphs, color type, sampler state). This must be compared with a trusted backend capability table, **not** merely a self-declared `materialSupport.supported` array in its report.
- Keep explicit source triangle counts, identifiers and attribute provenance after all transforms. Decode budget counts POSITION/NORMAL/INDICES/COLOR_0/UV/TANGENT, texture payloads, temporary and persistent surfaces. Account for peak during GLB decode and preparation, not merely steady framebuffer memory.
- Unsupported required features yield `BLOCKED_UNSUPPORTED_MATERIAL` (or a separately named geometry/camera failure) before final output; do not downgrade a source material silently and mark PBR `PASS`.

### B. Source scene structure
- Parse the GLB **once per source** and convert to structure-of-arrays buffers with immutable primitive/triangle IDs. Attribute arrays remain index-addressable; avoid exploding vertex data into three copies for each indexed triangle.
- Keep cached prepared world geometry in a bounded per-run session, keyed to SHA and transformation parameters; never put a user GLB or secret-containing path into a public perf artifact. Cross-session persistent preview caches are optional and must not be a canonical gate input.
- Explicit per-primitive material references, tangent frames, geometry winding and double-sided policy. Canonical neutral-clay substitutes its pinned material **at the shading level** rather than mutating the source scene in place.

### C–D. Visibility as a separate, compiled stage
- World->camera coordinates are computed once per **distinct camera** using vectorized contiguous buffers. Near-plane/frustum clipping must interpolate both homogeneous geometry and **original triangle barycentric provenance**, then project and bin conservative screen rectangles.
- Deterministic tile occupancy/prefix-sum/scatter, tile ownership, sorted source IDs, finite degenerate rejection, top-left coverage and stable depth ties. Opaque visibility produces a bounded `VisibilitySurface` (winner source triangle ID, depth and enough projected-barycentric/provenance data to recover source attributes at each visible pixel).
- For clipping: compute perspective weights relative to original **source vertices**; interpolating only newly clipped coordinates without provenance can distort COLOR_0 and UV. Handle the two-triangle fan, triangles crossing camera plane, and repeated/edge-on geometry with stable ownership.
- Avoid global per-triangle-per-tile color buffers; store compact source-indexed or viewport-indexed data. Never silently decimate certified geometry or drop tiny valid fragments for speed.
- Plan opaque sampling first; **MASK and BLEND** alter occlusion and sample ownership. Do not turn on either until per-material early/late alpha behavior and independent reference results are verified.
- Share design lessons and safe buffer conventions with `render_cpu_tiled.py`, but preserve a separately testable PBR visibility implementation or independently proven cross-renderer oracle. Sharing the entire diagnostic raster implementation would not give independent *geometric* verification, even if in another process.

### E–F. Material and color pipeline
- Shade **only depth-visible samples** in batches/tiles. Source RGB calculation must follow the glTF product: `linear(baseColorTexture sampled with correct sampler) * baseColorFactor * linear(COLOR_0)`. Texture sRGB is decoded **before** linear filtering; alpha is linear. Interpolation across triangles is perspective-correct.
- Reuse a numerically verified metallic-roughness BRDF, fixed/direct lights and pinned tone map (separate declared profiles when changing equations). `normal`, `object-id`, `albedo`, `neutral-clay`, `beauty` are **explicit pass semantics**; a changed material pipeline must not reuse the old exact profile identity.
- One consistent scene-linear->display transfer pipeline for all material sources; document what is an approximation of glTF (e.g., absent IBL, missing normal maps) and refuse a feature that the source requires when output claims full material fidelity.
- Group only render outputs with **identical camera projection/viewpoint/resolution/coverage/alpha rules**. The registered Hero may differ from current Normal/Object-ID/Albedo diagnostic camera: their visibility buffers MUST NOT be blindly reused just because they are all “front” views.
- The first target is opaque glTF metallic/roughness with COLOR_0 and baseColorTexture; implement opaque mask, transparency, tangents/normal texture, IBL and additional extensions only as separately gated capabilities.

### G. Publication, authority and versioning
- Preserve all existing `render_pbr.py` v1 behavior/neutral-clay report identity behind a frozen legacy worker and verify **old saved v1 report replay**. New worker, executable digest and `renderer.version` must be separately registered (provisional name `RefAs Independent PBR/2.0.0-candidate`).
- Introduce `refas.pbr-render-report/v2` if reporting visibility, material-inventory proof, coverage/near-clip statistics, stage timings, alpha/transfer profile or renderer binary binding changes trust meaning. Build a new normalizer/verifier rather than weakening the v1 profile validator. Source digest, frame digest, **per-view camera signature**, lighting/BRDF/color profile, declared+verified capabilities, executable/engine version, output PNG hashes and sample policy are independent fields.
- Distinguish `preview-only`, `geometry-diagnostic`, `material-evidence`, `neutral-clay shape` and `certification-eligible`. No backend, even a separate process or external GPU, may self-certify source resemblance. A trusted RefAs acceptance path compares required evidence, independent renderer/camera contracts and reference-image observations.
- Maintain staged output with rollback, no stale mixed PNG/manifest publication, typed `BLOCKED_TIMEOUT`/`BLOCKED_RESOURCE`/`BLOCKED_UNSUPPORTED`/`FAILED_ASSET` outcomes. Final certified renders must be freshly executed; only previews may reuse cached images with validated hashes.

## 3. Execution choices and independence

| Lane | Job | Implementation choice | Trust limit |
|---|---|---|---|
| CPU diagnostic v1.4 | fast geometric Normal/ID and resource triage | Existing tiled/Numba path | Never proves material appearance |
| Independent PBR v2 CPU | reproducible opaque COLOR_0/texture/full-source PBR fallback | Separate compiled tiled visibility + visible-only shading with NumPy/Numba optional | Separate process alone is not independent validation of generated geometry |
| External PBR adapter | full material and independent reference checking | Choose one *installed and validated* Blender/Filament/glTF-conforming engine; compare input/feature/support/license/OS constraints before implementation | Even an external engine does not measure similarity by itself |
| Trusted RefAs gate | authorize specific evidence claims | Independent verifier of source/frame/engine/shader/output plus reference-view comparison | Never accept a report as its own proof |

Prefer **one CPU vertical slice and one verified external adapter** over developing every material extension or rolling a full AAA renderer at once. Numba remains optional and is not introduced as a mandatory npm/skill dependency. Never promote preview, selected-triangle or substitute-GLB results into real-source completion.

### B. Full geometry vertical slice
- Use fixed miniature expected pixels and a user Monster Bed full-scene diagnostic job at 160px. Exact GLB triangle/primitive inventory; tested near clipping, two-fan mapping, backface/tie/winding, one/two different-depth overlapping materials, extreme microtriangles, tile/workers parity, memory/timeout refusal.
- Compare new PBR Normal/ID/depth/winner outputs to a **separately implemented oracle**, not just the same code under another entrypoint. Any difference must be attributed, not averaged away.

### C. Material vertical slice
- Independent known glTF test vectors for sRGB texture filtering, COLOR_0 float/normalized, baseColorFactor default, perspective-correct mixed-depth interpolation, UV sampler wrapping, GGX lighting and output transfer. Verify exact pixel arithmetic for invariant golden settings, and agreed tolerances for external physically-based references.
- Material feature scanner adversaries: unsupported glTF extensions and normal maps, missing required attributes, bad alpha, clip-through-fur and corrupted buffers must not become a misleading render PASS.

### D. Real Monster Bed
- Run 901,664 original indexed triangles and actual `COLOR_0` at 160px **and** 384px with no face subset, input SHA fixed to `30f8e135a34470366780b9b600040dff823171dfe857e7e4ab681c520a95f8d7`; observe warm/cold wall and peak RSS, stage counters, covered fragments, input/prepared/culled/clipped counts and actual PBR PNG SHA. Source asset is private and not committed.
- Compare 1/2/4/8 threads and 16/32/64 tile settings **on one pinned CPU**, plus near-plane and material reference goldens. Set quantified throughput acceptance limits **after** these measurements rather than inventing an SLA.
- Distinguish geometry success, shader/material fidelity, physically based output, source-photo resemblance, multiview and certification as separate results.

### E–F. External adapter and final gate
- Before choosing an external engine, verify actual binary/headless runtime, glTF COLOR_0/texture/roughness/alpha/double-sided handling, camera matrix conventions, color pipeline, licensing/packaging, environment and deterministic sample settings.
- Replay the same Monster Bed asset in the external engine with a registered source frame; independently check GLB/frame/lighting/renderer digests and images. Compare the CPU PBR result against a separate renderer **at matching camera, light and output transforms**, not arbitrary screenshots.
- Keep canonical registered Hero and seven other view roles intact, with explicit camera signatures and no false sharing. View material QA is not a source-resemblance certificate without the actual source/reference image and an independently authorized review gate.

## 5. Design risks and rejects

1. **Do not simply wrap the current Python inner triangle loop in another worker**: per-triangle Python work still scales poorly for 512k fur.
2. **Do not reuse raster visibility from different cameras**, or claim color accuracy from flat primitive averages. A high triangle-per-pixel density does not excuse missing geometry.
3. **Do not silently rewrite v1/neutral-clay output or trust identities**. Preserve historical report replay; v2 must identify changed render semantics.
4. **Do not advertise “independent” solely because the worker is spawned as another process**. Engine independence and source-resemblance authority need separate acceptance proofs.
5. **Do not unconditionally rebuild a whole GPU rendering stack inside RefAs**: adapter contracts should make existing engines first-class where full glTF/PBR features are required.
6. **Do not run full 1M/8-view stress in normal 20/22/24 CI**. Small deterministic goldens belong in PR CI; full user GLB and hardware measurements run only in isolated, opt-in jobs.
