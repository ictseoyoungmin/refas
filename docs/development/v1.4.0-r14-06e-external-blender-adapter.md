# R14-06E1 — Independently implemented Blender/Cycles glTF import

Status: **EXPERIMENTAL EXTERNAL BACKEND CANDIDATE**.
This is a Blender importer/Cycles PBR preview, **not source-photo
resemblance certification**. The bundled CPU PBR v2, historical v1
neutral-clay renderer, v1/v2 renderer report schemas, trusted spatial
gate and public `main` are unchanged.

## Architectural separation

- Host adapter: `render_external_blender.py` runs as a separate
  invocation using an actual installed `blender` binary. The caller
  SHA-binds the input GLB and canonical frame, validates the source
  glTF attribute/material inventory, typed-refuses unsupported
  texture transforms, animated/morphed meshes, required extensions,
  masked/blended materials, normal/emissive/roughness maps or resource
  excess, and fails as `R14E_BACKEND_UNAVAILABLE` if Blender is missing.
  **There is no silent fallback** to the RefAs CPU raster.
- Independent worker: `render_external_blender_worker.py` runs **inside
  Blender's bundled Python**, uses `bpy.ops.import_scene.gltf` and
  Blender **Cycles CPU** to render genuine imported meshes. It never
  invokes the RefAs geometry decoder, tiled visibility kernel or BRDF.
  It verifies the actual imported triangle count against source
  indexed triangles, checks Blender preserved COLOR_0 as an actual mesh
  color attribute and wired a color input node, and SHA-verifies the
  original GLB before and after rendering.
- Camera map: RefAs canonical-frame Hero (position, target, up, fovY)
  is converted from glTF Y-up to Blender Z-up as
  `(x,y,z) -> (x,-z,y)`; the camera orientation uses normalized
  forward/cross-up basis and vertical sensor fit, fov and near clip
  rather than arbitrary viewport navigation. The current user
  Monster Bed diagnostic frame is **NOT registered to its source
  photograph**. The Hero `registrationDigest` remains untrusted input
  in this adapter and cannot become a certification claim.
- Lighting: pinned **3 Blender SUN directional lights plus world
  ambient**, Cycles CPU fixed samples, Standard display view
  transform and source glTF metallic-roughness/vertexColor/PNG material.
  It is **not the identical BRDF/color/exposure profile** of the
  RefAs v2 direct-light preview. Therefore exact pixel RGB/SHA
  equality across CPU vs Blender is not an acceptance requirement;
  instead source attribute/geometry/camera provenance and independent
  visible-output behavior are separately checked.
- Output: `refas.external-pbr-preview/v1`, `claimScope =
  external-pbr-preview-only`, `certificationEligible = false`,
  `crossRendererEquivalence = NOT_ESTABLISHED`,
  `referencePhotoResemblance = NOT_EVALUATED`. Blender version,
  worker code digest, imported original triangle count and COLOR_0
  attribute inventory, camera/source byte hashes, output PNG hash,
  samples, engine and bounded timings are recorded. Publish to a new
  directory only after all checks, no source GLB included.

## Actual binary installation / validation

The isolated **opt-in** GitHub Actions workflow
`.github/workflows/r14-06e-blender-cycles.yml` triggers ONLY on
`bench/r14-06e-*` branches, not ordinary PR/develop CI.
It installs Blender from Ubuntu apt, reports actual binary version,
generates a deterministic indexed **SYNTHETIC** glTF 2.0 fixture
with an embedded PNG and nonuniform real COLOR_0 source vertices,
imports it using Blender's own glTF importer, renders 160px
Cycles CPU, and checks imported source triangle counts, actual
mesh color attributes and emitted PNG/result digest.
Neither private original Monster Bed GLB nor its provisional
frame is uploaded into that job.

The ordinary Node24 optional Python suite tests the source-bound
preflight on a real indexed GLB fixture, feature inventory,
typed backend-unavailable refusal and no false output files. It does
**NOT claim a Blender executable was tested** unless the opt-in
binary workflow succeeds and an actual produced PNG exists.

## Actual Blender 4.0.2 binary smoke, then causal shader verification

First opt-in real-GPU-independent **Cycles CPU** GitHub run
[#38740545925](https://github.com/ictseoyoungmin/refas/actions/runs/38740545925)
**SUCCESS** on Ubuntu 24.04 with Blender **4.0.2** installed by
apt. Synthetic 120-triangle indexed glTF with embedded PNG and COLOR_0
used Blender's glTF import (not RefAs raster), imported all
**120/120** faces and a **360-CORNER** color attribute named `Col`,
and produced a true **160x160** PNG SHA-256
`608f04570c7f5433b18785fb63c845cdc576c8729e689f392165c5b3492de25e`.
Observed `glbImport=184.612ms`, `cyclesRender=118.900ms`, total
Blender process `1523.089ms` on that runner; **not** a full asset
performance result. Artifact #11976451604 (30-day retention) contains
only generated synthetic output/report/fixture SHA.

A subsequent **stricter opt-in test** also requires the Blender
material node actually *connect* to the imported color attribute,
not merely contain an unconnected attribute node. It runs a
**geometry/texture-identical synthetic control** with COLOR_0 removed
and verifies that the independently shaded Cycles image changes by
a meaningful pixel count. This is a *causal material preservation
check*, not source-photo or physically perfect BRDF validation.
The original source and derived control carry separate SHA hashes.
Both synthetic GLBs are test-generated; the user Monster Bed original
is never stripped of COLOR_0 or uploaded to GitHub.
